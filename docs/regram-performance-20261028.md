# 长时间使用后整个窗口迟缓

用户确认 Intel/macOS 12 和 Apple Silicon 两边均会发生，开始时间不固定，退出重开后恢复。现象值得优先检查进程内资源或后台工作随使用过程累积，但不能据此直接认定内存泄漏，也没有证据把它归因于字体或 Intel。

本机 283380 重启后运行约 13 分钟时做了 5 秒只读取样。物理内存占用约 325.8 MB，峰值 401.1 MB；主线程 314 次采样里 307 次停留在事件循环等待，未抓到全窗口迟缓。该机器同时在构建两个架构的 Release，取样只能作为未复现状态的参考。原始记录在 `~/Library/Logs/RegramPerformance/20261028-283380/`。

同一进程第二次取样在 11:28:42，物理内存约 600.1 MB、峰值 616.2 MB，线程数由 42 变为 59；11:31 的 vmmap 显示约 439.5 MB 已分配堆内存。两次采样期间的用户操作和后台同步并未控制，且机器正在双架构构建，不能把该增长当作泄漏证明。

代码中的主要图片缓存已有数量、字节数、闲置时间上限，以及关闭页面和内存压力时的回收；内联表情会按窗口和可见区域停播。当前检查没有确认这些路径存在导致所述迟缓的泄漏。已运行的发送动作生命周期检查也不能代替卡顿现场的调用栈或内存趋势。

新增按需采样工具，不常驻、不改应用设置、不重启应用，不读取聊天正文。下次卡顿发生时先保留现场，在仓库中运行：

```sh
python3 tools/capture-regram-performance.py
```

工具记录进程运行时间、CPU/RSS、版本、系统与架构，以及默认 5 秒的线程栈和物理内存峰值，结果存入 `~/Library/Logs/RegramPerformance/`。需要在卡顿现场与恢复后的状态之间比较，才能判断是主线程布局、解码工作、锁等待还是内存增长；目前不能将该问题标记为已修复。
