# 分组、对话切换与后台任务阻塞复查

## 现象与范围

用户继续报告分组和对话切换仍然很慢，高负载和长时间运行时更明显；设置界面通常响应较快。按用户要求，本次从代码路径和隔离回归继续检查，没有自动切换其聊天、分组或设置页面。

用户进一步明确：有时负载莫名升高，聊天列表显示不全；聊天分组中的机器人分类也与其他端显示不一致。

本次重点检查主界面就绪依赖、共享准备/资源队列、同步等待、待取消订阅和过期列表计算。之前的上游合并、群组管理员入口、保护消息选词和链接悬浮预览修正保留。

## 确认并修正的路径

| 路径 | 原行为及影响 | 修正 |
| --- | --- | --- |
| 对话翻译初始状态 | 普通对话创建翻译上下文；状态 Promise 初始无值，首次配置处理排在共享 PrepareQueue。ChatController 的 appearanceReady 依赖该状态，即使没有开启自动翻译也会等待。 | 每个翻译上下文拥有 userInitiated 串行队列。首次状态、请求调度、结果回写、转录和摘要操作继续在同一个上下文队列处理。 |
| 发送媒体预览 | URL 和条目管线在共享 PrepareQueue 处理，部分媒体生成会等待资源生成或并行工作结束；完成回写也回到共享队列。 | 每个预览窗口使用自己的串行准备队列，URL、条目和完成回写共用该队列。 |
| 旧分组和分页更新 | 分组切换后，已经排队的旧列表快照仍可能进入条目构建。负对照中的 100 个旧快照全部创建条目。 | 在耗时映射及上一版本列表快照变更之前，检查当前分组和分页请求；过期快照跳过，当前快照继续按顺序处理。相同分组内仍有效的更新不会被合并丢弃。 |
| 分页来源和列表显示不同步 | previousChatList 在后台计算时就更新，可能先于实际显示；切换分组后的旧列表滚动也没有验证来源，可能把“全部聊天”的游标带到机器人分组。 | 列表变化携带分组、请求和源列表一起到主线程应用，分页来源在 merge 前一起更新。分页回调必须匹配已显示分组和当前请求；等待新分组或新分页时不再沿用旧游标。 |
| 骰子/表情缓存订阅 | animationEffect 和 interactiveSymbolData 都同步等待全局资源队列；后者即使 synchronous 为 false 也同步等待。取消标记还跨线程无保护地读写。 | 缓存状态和订阅使用每个缓存自己的串行队列，订阅异步安装，取消标记使用 Atomic；一次性订阅和取消后的订阅都能移除。加载入口也用 Atomic 避免重复启动。 |
| 设置账号角标 | 设置条目在共享 PrepareQueue 构建角标时，sync 参数让后台队列无限等待主线程计算角标。主线程忙时，其他共享队列任务也跟着等待。 | 去掉同步创建参数和信号量；角标到达后在主线程刷新，已有 ShortPeerRowView.onUpdate 触发布局。 |
| 主界面和置顶消息 | 主界面的两个布尔就绪值仍在共享 PrepareQueue 合并；置顶消息处理也依赖该队列。 | 就绪值在主队列轻量合并；置顶消息沿用对话已有的专用历史队列。 |

骰子接口保留原有调用参数，但不会再为了 synchronous 提示跨队列阻塞；首个缓存值可能在下一个队列轮次到达，调用方继续显示原有缩略图。生日表情效果调用补上主队列交付，保证异步缓存结果到达后仍在主线程操作界面。

## 其他等待的检查结论

播放器的 FFmpeg 读回调运行在专用读取线程，取消信号能够唤醒等待；图片画布动画导出有自己的队列；聊天导出的等待循环会定期检查取消。退出应用时的 Postbox 队列保护只用于退出。它们不能仅凭出现 wait 就认定为日常分组切换的原因，本次没有改写这些协议。

TabAllBadgeItem 创建设置标签图标时仍有一次 activeAccounts 首值等待。正常主界面建立时该 Promise 已持有账号值，和每次分组计算的路径不同；本次没有把它认定为已复现的长期积压来源。社区分类和摘要仍有数据库依赖，本次没有修改 TelegramCore 或现有子模块内容。

这些修改移除了已确认的共享队列依赖和部分过期工作。没有捕获本轮真实账号的长期高负载卡顿，不能据此宣称所有“非常慢”的场景已经消失。
